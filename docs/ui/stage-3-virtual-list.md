# 阶段 3（UI）：列表虚拟化与硬上限

> 分支 `ui/virtual-list` · 父提交 `ui/panel-switch`（阶段 2）

## 1. 做了什么

### 1.1 D 档：三个无上限列表加上硬上限（Q11=a）

| 列表 | 原状态 | 上限 | 超出时的反馈 |
|---|---|---|---|
| 会话标签 | **无上限**，开 40 个会话挂 40 个标签节点 | **20** | 标签条尾部显示 `+N`，悬停说明还有几个未显示 |
| 传输列表 | **无上限**，批量传 500 个文件挂 500 行 | **200** | 底部汇总仍按全量统计（进度数字不缩水）|
| 设备发现 | **无上限**，/24 网段就有 254 个候选 | **500** | 列表顶部提示「仅显示前 500 项，共 N 项」|

三处都**不是静默截断** —— 静默截断比不截断更坏（用户以为数据丢了）。

### 1.2 A 档：两个双栏目录列表改为真虚拟滚动

| 文件 | 改动 |
|---|---|
| `RemotePane.tsx` | 删掉 `ROW_LIMIT=300` 截断 + 「还有 N 项」提示，改为 `useVirtualizer` |
| `LocalPane.tsx` | 同上 |
| `styles/index.css` | 新增 `.file-row-token-inner`（虚拟行内层：高度由外层定位盒给定，内层只负责排版与过渡）|
| `package.json` | 新增 `@tanstack/react-virtual@3.14.26`（Q3=a）|

**关键约束：选中/全选语义仍基于 `files` 全量**，不受「当前渲染了哪几行」影响。
否则 `Ctrl+A` 会退化成「全选可见部分」—— 这是虚拟化最典型的语义回归。

行高固定 24px（token 开启时）或 22px（旧样式）：虚拟化靠「索引 × 行高」定位，
固定高才能省掉 `measureElement` 的逐行测量开销。这与阶段 1 的行高口径一致。

## 2. 没做完的部分（如实交代）

原计划 A 档 5 个列表，**完成 2 个**（远端/本地目录）。剩下 3 个未做，理由各不相同：

| 列表 | 未做原因 |
|---|---|
| 会话文件树 `SessionFileTree` | 是**嵌套树**（可展开/折叠），行高随层级与展开状态变化，固定行高虚拟化会破坏树语义；需要「扁平化 + 动态 measure」两步改造 |
| 命令历史 `HistoryPanel` | 已有 `limit: 300` 且**在 IPC 层截断**（主进程只回 300 条），虚拟化要先把 limit 提到分页/无限，改动跨进程 |
| 诊断结果 `DiagnosticsPanel` | 按 section 分组、每组条目数不定，同样是变高列表 |

这 3 个当前**都有截断**，不会无限增长，属于「功能性可接受」。建议作为阶段 3.5 单独处理。

## 3. 一次失败的验证尝试（也如实交代）

我试图写 `verify-virtual-list.cjs`：自起 lab SFTP + 造 10000 个文件 → 打开面板 →
断言「DOM 行数 < 200」且「scrollHeight ≈ 总项数 × 行高」。**没跑通**，两处卡住：

1. 第一版先 `location.reload()` 再 evaluate → reload 销毁 CDP target，评估超时；
2. 第二版改为直接 `window.api.session.open` 建会话 → 会话状态始终为空（脚本里没走
   「先保存连接、再由渲染层侧栏触发」的真实链路），随后又超时。

**这个脚本已删除**，没有放进门禁 —— 一个 FATAL 的脚本留在仓库里比没有更糟。
当前虚拟化的验证依据是：typecheck/lint 干净、18 项 UI e2e 通过（SFTP 列表承载真实文件操作）、
以及代码层的行高/定位推导。**这是弱于原计划的验证强度，我明确标注为缺口。**

## 6. 补做：虚拟化的自动化验证（本阶段收尾）

上一轮记录的「验证缺口」已补齐。

### 6.1 换思路：只验渲染层，不碰 SFTP

前两版失败的原因是**纠缠在数据链路上**（reload 销毁 CDP target / 脚本自建会话状态为空）。
但虚拟化要证明的是「DOM 行数被窗口化且滚动覆盖全量」，**与数据从哪来无关**。

所以改成：通过 `window.__lazy_test`（项目已有的测试桥，`App.tsx:528`）往 sftpStore 注入
10000 条形制等价的假目录项，直接断言渲染结果。不连 SFTP、不建会话、不 reload。

### 6.2 8 条断言（实测输出）

```
PASS  测试桥可用（需 ZM_TEST=1 构建）
PASS  已注入 10000 条目录项
几何: {"found":true,"rows":39,"scrollH":220008,"clientH":677}
PASS  存在可滚动的列表容器
PASS  渲染行数远小于总项数（窗口化生效）      ← 39 行 vs 10000 项
PASS  滚动高度覆盖全量（>= N × 20px）          ← 220008 >= 200000
PASS  滚动高度 <= N × 40px（未虚增）           ← 220008 <= 400000
滚动: {"before":"f-00000...","after":"f-04992...","rows":47}
PASS  滚到中部后仍只渲染少量行                 ← 47 行
PASS  滚动后首行内容变化（窗口化而非全量渲染）
通过 8  失败 0
```

**39 行 vs 10000 项**，滚动到底部时 47 行 —— 窗口化确实成立。

### 6.3 变异测试（确认有区分度）

把 `overscan: 8` 改成 `overscan: 100000`（等价于关闭窗口化）：

```
几何: {"found":true,"rows":10000,...}
FAIL  渲染行数远小于总项数（窗口化生效）      -> 10000
FAIL  滚到中部后仍只渲染少量行                 -> 10000
FAIL  滚动后首行内容变化                       -> before === after
通过 5  失败 3
```

三条同时变红，证明这组断言测的是「窗口化」本身，不是别的东西。

### 6.4 为什么不放进主门禁

本脚本依赖 `ZM_TEST=1` 构建（才挂测试桥），而主门禁 `run-all-verify` 用普通构建。
挂在里面会**稳定红**，而「一条永远红且与修复无关的用例」会训练所有人忽略门禁 —— 
这比没有更糟。所以：

| 做法 | 说明 |
|---|---|
| 文件名 `check-virtual-list.cjs` | 主门禁只 glob `verify-*.cjs`，天然排除 |
| `npm run test:vlist` | 包装器：构建测试版 → 跑断言 → **恢复普通构建**（防止测试钩子残留进后续 e2e） |

恢复普通构建这步是必须的：`out/` 里若留着带 `window.__lazy_test` 的产物，
后续 e2e 会跑在一个多出全局对象的环境里，问题极难查。
